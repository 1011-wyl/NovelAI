# NovelAI 长篇小说创作闭环整体策划书

> 文档定位：产品策划、交互设计和后续技术实施的统一依据  
> 当前阶段：策划稿，不代表功能已经实现  
> 参考方向：NovelAI 现有生成与记忆能力、OpenFic 写作工作区与 AI 修改交互

## 1. 项目定位

NovelAI 不应只被定义为“输入要求后生成小说章节的工具”，而应被设计为一套帮助用户持续掌控长篇小说的创作工作系统。

系统的核心价值不是单次生成更多文字，而是让用户能够：

- 从一个尚不完整的想法建立可执行的故事蓝图；
- 在生成前控制每一章要完成的叙事任务；
- 在生成后像使用写作软件一样阅读、编辑和重写；
- 让 AI 的修改经过用户批准，而不是直接覆盖正文；
- 在正文变化后同步处理人物、世界规则、时间线、伏笔和后续章节；
- 随时查看版本、恢复修改，并在未来支持故事分支。

产品最终应形成以下闭环：

```text
创作意图
  → 故事种子
  → 故事蓝图
  → 章节任务
  → 正文生成
  → 阅读与修订
  → 修改影响分析
  → 记忆与后续规划更新
  → 下一章
```

## 2. 产品目标与非目标

### 2.1 产品目标

1. 让没有完整大纲的用户也可以从一个想法开始创作。
2. 保留“先确认创作方案、再逐章生成”的现有创作方式。
3. 把目前的作品阅读页升级为真正的章节写作工作区。
4. 建立手工修改、AI 修改、版本、记忆和后续剧情之间的闭环。
5. 降低用户修改早期章节时对后续内容失控的风险。
6. 让 AI 的上下文、写入动作和记忆变更对用户可见、可批准、可撤回。

### 2.2 第一阶段非目标

- 不实现一键生成整本小说。
- 不实现多人实时协作。
- 不实现云端账号、跨设备同步和在线发布平台。
- 不引入新的大型前端框架重写整个项目。
- 不在第一阶段实现完整故事分支合并。
- 不让 AI 在没有用户批准的情况下直接修改正式正文。

## 3. 目标用户与核心场景

### 3.1 目标用户

- 有故事想法但不会搭建完整大纲的新手作者；
- 已有设定，希望借助 AI 提高产出效率的网文作者；
- 需要反复打磨人物、剧情和语言的长篇创作者；
- 希望掌控故事而不是接受 AI 黑箱生成结果的用户。

### 3.2 核心场景

1. 用户输入一句创意，让系统整理为可以确认的故事蓝图。
2. 用户确认下一章的目标和冲突，再让 AI 生成正文。
3. 用户阅读正文时手工修改，并自动保存修改草稿。
4. 用户选中一段文字，让 AI 润色、精简、扩写或改写。
5. 用户先查看修改差异，再批准或拒绝 AI 写入。
6. 修改正式提交后，系统展示人物、世界和时间线发生了什么变化。
7. 修改早期章节后，系统指出哪些后续章节受到影响，而不是让风险保持隐形。

## 4. 产品结构

### 4.1 全局层

全局导航只负责跨作品能力：

- **作品库**：默认首页，创建、搜索、筛选和继续作品。
- **仪表盘**：写作活动、调用统计和成本信息。
- **系统设置**：运行能力、模型、外部能力和本地偏好。

“创建小说”不再占用顶级导航，而是作品库中的主要操作。

### 4.2 作品工作空间

用户进入一本小说后，界面始终保持当前作品上下文，并提供：

- **概览**：作品状态、下一步任务、最近章节和风险提示。
- **故事蓝图**：故事承诺、结构、人物驱动和世界约束。
- **写作**：章节目录、正文编辑器和 AI 创作助手。
- **设定与记忆**：人物、世界规则、时间线、伏笔和研究资料。

作品名称、状态和返回作品库入口始终可见，避免用户在多个全局页面之间反复确认当前项目。

## 5. 三层创作闭环

### 5.1 全书闭环

负责小说长期方向：

```text
故事想法 → 故事蓝图 → 阶段目标 → 已完成章节 → 蓝图校正
```

当章节发展与最初方案出现明显偏差时，系统应提示用户更新蓝图或修正章节，而不是静默积累矛盾。

### 5.2 章节闭环

负责每章从计划到正式入库：

```text
章节任务 → 生成草稿 → 审核 → 用户阅读 → 修订 → 正式版本 → 记忆变更
```

章节任务必须至少描述：

- 本章目标；
- 开场状态；
- 核心冲突；
- 必须发生的事件；
- 关键人物选择；
- 选择产生的代价；
- 章末钩子；
- 不允许违反的设定。

用户可以锁定其中部分内容，再要求 AI 重新规划其他部分。

### 5.3 段落闭环

负责高频微观修改：

```text
选择正文 → 指定意图 → AI 生成候选修改 → 差异预览 → 批准/拒绝 → 撤回
```

段落级闭环必须足够轻量，常用操作不要求用户重复编写完整提示词。

## 6. 核心模块策划

### 6.1 作品库

作品库不是静态文件柜，而是整个创作系统的任务中心。

每张作品卡片显示：

- 书名、类型和项目状态；
- 正式章节数量和最近更新时间；
- 当前创作阶段；
- 最需要用户处理的下一项任务；
- “继续创作”主按钮；
- 暂停、恢复、归档和删除等次级操作。

主按钮根据项目状态动态变化：

| 项目状态 | 主按钮文案 | 跳转位置 |
|---|---|---|
| 方案未确认 | 继续完善方案 | 故事蓝图 |
| 方案已确认、无章节 | 开始第一章 | 章节任务 |
| 有 READY 章节 | 继续写作 | 最近章节 |
| 有未提交修改 | 继续修订 | 对应章节编辑器 |
| 章节生成失败 | 处理失败章节 | 作品概览/生产流程 |
| 有连续性风险 | 查看影响 | 影响分析面板 |

支持按关键词、状态和更新时间筛选。封面第一阶段使用题材与书名生成的 CSS 视觉卡，不引入上传与文件管理依赖。

### 6.2 从想法创建小说

创建流程采用“灵感优先、参数后置”的渐进式设计。

第一步只要求：

- 核心想法；
- 读者频道；
- 主类型；
- 可选书名。

系统生成“故事种子卡”：

- 一句话故事；
- 核心冲突；
- 主角欲望；
- 最大阻力；
- 独特卖点；
- 读者期待；
- 潜在创作风险。

用户确认方向后，再展开阅读体验、核心元素、感情线、排除项、篇幅和更新计划等高级选项。

创建成功后直接进入故事蓝图，不停留在空白项目首页。

### 6.3 故事蓝图

故事蓝图是会随作品演化的模型，不是确认后冻结的初始化表单。

蓝图分为四层：

1. **故事承诺**：题材、卖点、目标体验和读者契约。
2. **故事结构**：主线、阶段目标、重大转折和结局方向。
3. **人物驱动**：人物欲望、秘密、矛盾、关系和成长弧。
4. **世界约束**：世界规则、力量代价、资源边界和知识边界。

修改蓝图时系统先生成影响提示，例如“这一规则已被第 3、7、9 章引用”。用户确认后才产生新版本。

第一阶段继续复用现有方案编辑、局部重生成、版本比较和恢复能力，在界面和数据表达上逐步升级为故事蓝图。

### 6.4 章节任务与章节生成

“生成下一章”调整为两阶段操作：

1. 生成并展示章节任务。
2. 用户确认或修改后生成正文。

系统允许用户：

- 修改章节任务；
- 锁定某些字段；
- 按意见重新规划；
- 确认并生成；
- 在生成失败后复用任务重试。

正文仍然经过现有的可读性审核、Story Skills 连续性审校、去 AI 味处理和记忆提取。

### 6.5 写作工作区

桌面采用三栏结构：

```text
章节目录 | 正文编辑器 | AI 创作助手
```

#### 左栏：章节目录

- 卷与章节层级；
- 状态、版本和风险标记；
- 章节搜索；
- 生成下一章入口；
- 当前章节高亮；
- 可拖动调整宽度。

#### 中栏：正文编辑器

- 标题和正文直接编辑；
- 800ms 防抖保存修订草稿；
- 保存状态、字数、版本和更新时间；
- 撤销、重做和版本历史；
- 选中文字后的快捷修改工具条；
- “应用修订”用于生成正式新版本；
- 未提交修改在刷新和重新进入后仍然存在。

自动保存只保存工作草稿，不立刻触发记忆重建和后续章节处理。正式提交必须是显式动作，避免用户一次普通输入造成不可逆的连续性变化。

#### 右栏：AI 创作助手

提供三种模式：

- **顾问**：分析问题但不产生正文写入；
- **共创**：提供候选方案，由用户自行选择；
- **编辑**：生成可执行修改，并进入权限与差异流程。

AI 自动获得当前章节、选中文字、故事蓝图、相关人物、世界规则和最近章节摘要，但界面必须显示本次使用了哪些上下文。

### 6.6 选中文本快捷操作

选择正文后显示轻量工具条：

- 润色；
- 精简；
- 扩写；
- 增强画面；
- 调整对白；
- 加入对话。

前五项直接生成修改差异；“加入对话”用于附带复杂创作要求。

### 6.7 AI 修改授权与差异

`edit_chapter` 和 `rewrite_chapter` 默认权限固定为 `ask`。

AI 修改流程：

1. 用户提出要求或使用快捷操作。
2. AI 生成待执行修改。
3. 对话区显示修改说明、差异和增删统计。
4. 用户选择批准或拒绝。
5. 批准后写入修订草稿，不直接绕过正式提交。
6. 用户可以撤销本次修改或回滚到某条消息之前。
7. 点击“应用修订”后才生成正式章节版本。

AI 普通回答不得伪装成修改操作；待批准、已批准、已拒绝和已回滚必须有清晰状态。

### 6.8 记忆变更确认

正式提交章节后，不只显示“保存成功”，还要显示本章对故事状态造成的变化：

```text
人物
+ 林夏得知父亲仍然活着
~ 周明对林夏：怀疑 → 暂时合作

世界
+ 黑潮只能在月落后出现

时间线
+ 第 8 章：调查组进入旧港区

伏笔
+ 红色录音带首次出现
```

第一阶段允许用户查看变更；后续阶段再支持逐条修正、删除或补充后提交到正式记忆。

### 6.9 修改影响分析

长期目标是不再直接删除所有后续章节，而是建立影响状态：

- `NORMAL`：未发现影响；
- `CHECK_REQUIRED`：需要重新检查；
- `CONFLICTED`：发现明确冲突；
- `REPAIRED`：已经修复。

修改第 N 章后，系统分析其后章节并给出：

- 明确冲突的章节；
- 可能受影响的章节；
- 暂未发现影响的章节；
- 建议局部修复或重新生成的位置。

由于当前项目已经实现“重置当前章及后续章节”的规则，第一阶段先保留该规则，但必须做到：

- 正式提交前显示受影响章节数量；
- 后续内容先归档再重置，不进行不可恢复的物理删除；
- 数据结构预留后续影响状态和故事分支能力。

### 6.10 版本与故事分支

每次手工提交、AI 提交和回滚都生成不可变版本，记录来源、时间、修改说明和关联会话。

故事分支作为后续能力：用户可以从任意正式章节建立另一条剧情路线，分支分别拥有章节、人物状态、时间线、伏笔和 AI 会话。第一阶段不实现分支 UI，但版本和关联设计不得假设每本书永远只有一条不可分叉的正文链。

## 7. 视觉与交互设计系统

整体采用内容优先的 Minimalism / Swiss 风格，并以 OpenFic 的编辑工作区为直接参考。

### 7.1 视觉原则

- 以黑、白、中性灰为主，品牌色只用于主要动作、焦点和选中状态；
- 不使用大面积紫色 AI 渐变；
- 少阴影、细边框、稳定网格；
- UI 使用系统无衬线字体，正文使用适合长阅读的中文衬线字体；
- 图标统一使用 SVG；
- 状态不能只依赖颜色，必须同时使用文字或图标。

### 7.2 响应式

- `≥ 1200px`：完整三栏，左右栏可调整宽度；
- `768–1199px`：目录保持窄栏，AI 使用右侧覆盖层；
- `< 768px`：正文单栏，目录为抽屉，AI 为全屏覆盖层；
- 在 320、375、414、768、1024 和 1440 宽度下验证；
- 页面主体不出现整体横向滚动。

### 7.3 无障碍与反馈

- 普通文字对比度不低于 4.5:1；
- 所有主要操作可用键盘完成；
- 焦点顺序与三栏视觉顺序一致；
- 可见焦点不能被取消；
- 点击区域至少 44×44px；
- 保存、生成、批准和提交都有明确进行中、成功和失败反馈；
- 支持 `prefers-reduced-motion`；
- 删除、重置后续章节和覆盖版本必须二次确认。

## 8. 概念数据模型

在现有项目、章节、版本、人物、世界和时间线基础上，逐步补充：

- **StorySeed**：从原始想法提炼的故事种子；
- **StoryBlueprintVersion**：故事蓝图版本；
- **ChapterTaskVersion**：章节任务版本与锁定字段；
- **ChapterWorkingCopy**：正文修订草稿；
- **AssistantSession / Message**：章节级 AI 会话；
- **AssistantChangeSet**：待批准、已批准、已拒绝或已回滚的修改；
- **MemoryChangeSet**：正式章节提交产生的记忆变化；
- **ChapterImpact**：章节修改对后续章节的影响；
- **StoryBranch**：未来的故事分支。

正式章节、正式记忆和当前主线仍由 SQLite 事务保证一致性。AI 输出在用户批准前只能存在于候选记录或工作草稿中。

## 9. 分阶段路线图

### 阶段一：建立可用的修订闭环

- 章节工作草稿与自动保存；
- 正文编辑器；
- 选中文本加入对话；
- AI 顾问、共创和编辑模式；
- 修改差异、批准、拒绝和回滚；
- 正式章节版本；
- 提交后的记忆重建；
- 后续章节归档与重置提示。

完成标志：用户可以从一章 READY 正文开始，完成“阅读—修改—批准—提交—记忆更新—继续生成下一章”的完整闭环。

### 阶段二：重构创作入口

- 作品库任务卡片；
- 作品级工作空间；
- 灵感优先的新建小说流程；
- 故事种子卡；
- 现有创作方案升级为故事蓝图界面。

完成标志：用户不需要理解系统内部页面结构，也能从一句想法进入正确的下一步。

### 阶段三：增强章节控制

- 章节任务确认页；
- 任务字段锁定与局部重新规划；
- 记忆变更查看和人工修正；
- 后续章节影响检测；
- 对冲突章节的局部 AI 修复。

完成标志：修改早期剧情后，用户能够清楚知道影响范围并选择处理方式。

### 阶段四：高级长篇能力

- 故事分支；
- 分支对比与设为主线；
- 蓝图与正文双向影响分析；
- AI 主动发现人物、时间线和伏笔风险；
- 更完整的成本和质量指标。

## 10. 成功指标

第一阶段不以“生成字数”作为唯一指标，而关注：

- 从创建作品到确认故事蓝图的完成率；
- 从确认蓝图到生成第一章的完成率；
- 用户阅读后发生手工或 AI 修订的章节比例；
- AI 修改的批准率和撤回率；
- 章节修改后连续性错误数量；
- 用户因修改早期章节而永久丢失内容的次数，应为 0；
- 从打开作品到进入有效创作状态所需时间；
- FAILED 或 HUMAN_REQUIRED 状态的恢复成功率。

## 11. 风险与控制

### 11.1 过早追求完整功能

风险：作品库、蓝图、编辑器、AI、分支同时开发，导致每个模块都无法形成完整价值。

控制：优先完成一章正文的纵向修订闭环，再扩展导航和高级功能。

### 11.2 AI 修改与正式数据混淆

风险：AI 回复、候选改写和正式正文缺少明确边界。

控制：候选修改、工作草稿和正式版本采用不同状态与存储，正式写入必须经过用户批准和提交。

### 11.3 早期章节修改造成数据损失

风险：沿用当前重做逻辑会永久清理后续内容。

控制：先归档后重置；长期改成影响分析和分支，不直接物理删除用户内容。

### 11.4 记忆提取失败

风险：正文已经改变，但人物和时间线仍为旧状态。

控制：正式提交作为服务端事务流程；提取失败时保留工作草稿，不替换正式章节。

### 11.5 三栏界面在小屏不可用

风险：照搬桌面 OpenFic 布局导致移动端拥挤。

控制：移动端只保留正文主视图，目录与 AI 分别使用抽屉和覆盖层。

## 12. 第一实施模块建议

建议第一个修改模块不是作品库，也不是单纯更换视觉样式，而是：

> **“阅读与修订工作台”纵向 MVP**

它应以一章现有 READY 正文为入口，一次性贯通：

```text
加载章节
→ 编辑正文
→ 自动保存工作草稿
→ AI 对话引用正文
→ 差异预览
→ 批准或拒绝
→ 正式提交版本
→ 更新记忆
→ 处理后续章节
```

选择它作为起点的原因：

1. 它直接解决当前系统最大的断点：生成以后只能阅读，不能继续共同创作。
2. 它能验证产品最关键的差异化——AI 修改是否真正可控。
3. 它会迫使版本、权限、记忆和连续性规则先变得可靠。
4. 后续作品库、故事蓝图和章节任务都可以围绕这套稳定内核接入。
5. 如果先改作品库，短期虽然更好看，但用户核心创作能力没有变化。

该模块内部的实施顺序为：

1. 工作草稿、版本和安全提交的后端内核；
2. 三栏工作区和正文编辑器；
3. AI 会话与选中文本引用；
4. 差异、批准、拒绝和回滚；
5. 记忆变更和后续章节处理；
6. 桌面、移动端和无障碍验收。

第一模块完成后，再开始作品库与作品级工作空间重构，能够避免先搭建漂亮外壳、后续又因为修订模型变化而返工。

## 13. 文档与验收要求

每完成一个用户可见阶段，必须同步更新 `docs/USER_GUIDE.md`，并确认 README 中的用户指南链接有效。

实施验收至少覆盖：

- 原有方案确认和逐章生成流程没有回归；
- 自动保存失败不会丢失编辑内容；
- AI 未获批准不能修改正文；
- 差异和版本来源可以追踪；
- 修改早期章节前明确告知后续影响；
- 后续章节即使被重置也可以从归档恢复；
- 正式正文、人物记忆和时间线不会出现半提交状态；
- 键盘可完成核心操作；
- 320px 至 1440px 宽度下主要流程可用。
