# 章节生成、质量审核与自动修订统一修复文档

> 适用项目：NovelAI  
> 文档用途：交给 Cursor 直接执行  
> 核心目标：写作与审核使用同一质量契约；章节质量总分 **严格大于 60 分** 即通过；自动修订只能让最终采用版本变好，不能用低分稿覆盖高分稿；彻底清除旧的冲突判定代码。

## 1. 问题背景

当前章节生成链路存在以下已确认问题：

1. 页面声明或用户理解为“质量分超过 60 分即可通过”，但后端还存在单项 75 分、平均 82 分、问题严重度等额外质量门槛，造成 77 分仍显示未通过。
2. 写作模型、审核模型、自动修订模型没有完整使用同一份质量契约。写作时不知道全部审核要求，审核时又使用额外规则。
3. 自动修订没有保证结果单调变好，出现过 `91 → 61 → 77`，低分新稿覆盖高分旧稿。
4. 目标字数只是提示词中的软要求。生成后虽然检查了字数，但没有稳定执行“统计—补写—复检”的闭环。
5. 章节长度仅达到目标的 87% 时，页面把长度问题与质量失败混在一起，用户无法判断真正失败原因。
6. 前端展示的是最低项、轨迹或第一条问题，但后端最终判定可能来自另一项隐藏条件，展示与判定不一致。
7. 旧常量、旧分支、旧兼容路径仍可能被调用，即使新增了质量契约，也无法保证运行时只走新逻辑。

本次修复必须从数据契约、生成、预检、审核、修订、状态机、持久化和前端展示整个链路处理，不能只修改一个阈值或一段提示词。

---

## 2. 不可变的产品规则

以下规则是本次实现的唯一标准，不得另加隐藏质量门槛。

### 2.1 唯一质量通过规则

```text
quality_score > 60.0  →  PASS
quality_score <= 60.0 →  REVISE（仍有自动修订次数）
quality_score <= 60.0 →  NEEDS_ATTENTION（自动修订次数已用完）
```

注意：这里是“严格大于 60”，因此 `60.0` 本身不通过，`60.01` 通过。显示时不得因四舍五入造成误解，后端应使用原始数值判断，前端至少显示一位小数。

以下内容不得再作为独立的质量否决条件：

- 可读性单项必须达到 75 分；
- 可读性平均分必须达到 82 分；
- 任意 `MAJOR` 自动否决；
- 任意 `BLOCKER` 在总分已经超过 60 时再次执行质量否决；
- 长度 90% 等预检条件直接修改质量审核结论；
- 某个审核器自身返回的 `PASS/REVISE` 覆盖统一总分结论。

审核维度、问题严重度和文字建议仍可保留，但用途只能是：

1. 计算统一总分；
2. 生成自动修订指令；
3. 向用户解释扣分原因。

它们不能再形成第二套隐藏通过条件。

### 2.2 技术失败与质量失败必须分开

以下情况属于“生成未完成”或“技术失败”，不进入质量评分：

- LLM 请求失败、超时或返回空正文；
- 输出被模型长度上限截断；
- 返回格式无法解析且无法恢复；
- 正文缺失；
- 字数尚未完成自动补写流程。

技术失败状态不得显示为“质量不通过”。建议使用：

```text
GENERATION_FAILED
LENGTH_REPAIRING
LENGTH_NEEDS_ATTENTION
QUALITY_REVIEWING
QUALITY_REVISING
PASSED
QUALITY_NEEDS_ATTENTION
```

### 2.3 字数达标规则

当用户选择“约 3000 字”时，采用范围而不是要求精确等于 3000：

```text
min_length = ceil(target_length * 0.90)
max_length = floor(target_length * 1.10)
```

因此目标 3000 字时：

- 2700～3300 字：长度达标；
- 2100～2699 字：自动定向补写；
- 少于 2100 字（低于目标 70%）：正文严重不完整，重新生成或分场景续写；
- 超过 3300 字：标记超出建议范围；只有明显影响产品限制时才压缩，不能直接判定质量失败。

前后端必须使用同一计数函数和同一口径。中文建议统计可见正文中的汉字、数字和拉丁字母，忽略 Markdown 标记及纯空白；不得后端按字符、前端按空格分词。

## 3. 建立唯一的写作—审核质量契约

### 3.1 单一事实来源

在 `novel_agent/features/chapter_review/quality_spec.py` 中建立或重构唯一的 `ChapterQualityContract`。所有阈值、评分维度、权重、字数范围和修订上限只能从这里读取。

建议结构：

```python
@dataclass(frozen=True)
class ChapterQualityContract:
    pass_score_exclusive: float = 60.0
    desired_generation_score: float = 85.0
    min_length_ratio: float = 0.90
    max_length_ratio: float = 1.10
    severe_shortage_ratio: float = 0.70
    max_length_repairs: int = 2
    max_quality_revisions: int = 2
    dimensions: tuple[QualityDimension, ...] = (...)
```

`desired_generation_score=85` 是写作目标，不是隐藏通过线。它用于要求初稿尽量写好；最终是否通过仍然只由 `quality_score > 60` 决定。

### 3.2 同一契约必须贯穿完整链路

以下模块必须接收同一个契约实例或同一份序列化快照：

```text
章节任务规划
  → 初稿提示词构建
  → 初稿生成
  → 字数预检和补写
  → 质量审核提示词构建
  → 总分计算
  → 自动修订提示词构建
  → 候选稿比较
  → 最终状态判定
  → 前端展示
```

禁止写作提示词、审核提示词和工作流各自硬编码另一套阈值。

### 3.3 契约需要包含的内容

至少包含：

- 章节编号、是否第一章；
- 目标字数及可接受范围；
- 本章必须完成的剧情节点；
- 可使用的背景设定和人物状态；
- 不可虚构或改变的事实；
- 审核维度、权重和明确评分标准；
- 统一通过线 `> 60`；
- 写作目标分数（建议 85）；
- 长度修复次数和质量修订次数；
- 当前轮允许修改的范围。

第一章不得要求匹配不存在的上一章，也不得因为没有前文铺垫而产生“违反前文章节档案”的问题。第一章契约应明确要求自然完成：主角基本定位、当前处境、必要背景、开篇事件或冲突、后续钩子；但不要机械堆砌设定说明。

## 4. 统一评分与最终判定

### 4.1 统一总分

所有维度均使用 0～100 分，并通过一个明确的加权公式计算总分：

```python
quality_score = sum(dimension.score * dimension.weight for dimension in dimensions)
```

要求：

- 所有权重之和必须等于 1；
- 缺失维度必须视为审核结果无效并重试解析，不能偷偷按 0 分或满分处理；
- 最终只产生一个 `quality_score`；
- `minimum_dimension_score`、`average_readability_score` 可以展示，但不能参与第二次通过判定；
- 所有 reviewer 的局部 `decision` 字段应删除，或者仅保留为展示信息且不得进入状态机。

### 4.2 唯一判定函数

只保留一个公开判定函数，例如：

```python
def decide_quality(score: float) -> QualityDecision:
    if score > QUALITY_CONTRACT.pass_score_exclusive:
        return QualityDecision.PASS
    return QualityDecision.REVISE
```

所有调用者必须调用该函数，不能自行写 `score >= ...`、单项阈值或严重度分支。

### 4.3 问题严重度的处理

保留 `MINOR/MAJOR/BLOCKER` 时，其含义改为修订优先级：

- `MINOR`：轻微优化建议；
- `MAJOR`：本轮优先修复；
- `BLOCKER`：最高优先级扣分问题和明确提示，但不再绕过统一总分另行否决。

如果产品确实需要内容安全或技术完整性硬拦截，应放到独立的安全/技术预检状态中，不能借用质量审核的 `BLOCKER` 制造隐藏质量门槛。

## 5. 字数生成闭环

### 5.1 初稿生成前

根据目标中文字数动态计算足够的模型输出额度，并预留安全余量。`max_tokens` 只能作为上限，不能当作目标字数保证。

写作提示词必须明确：

- 目标字数；
- 合格范围；
- 各场景建议字数预算；
- 不要用重复句、空洞总结或无意义描写凑字数；
- 只返回正文，不返回字数声明、解释或审核过程。

### 5.2 初稿生成后

先运行确定性的字数统计，再决定是否进入质量审核：

```text
范围内
  → 进入质量审核

70%～90%
  → 计算缺口
  → 定向补写
  → 合并
  → 重新统计

低于 70%
  → 判断是否截断
  → 从断点续写或重新按场景生成
```

例如目标 3000、实际 2610，不应整章重写。应要求补充约 430～500 字，并说明：保持已有剧情、人物状态和结尾方向不变；优先补足过渡、动作、环境或有效对话；不得复述已有内容。

### 5.3 字数修复与质量修订分离

字数修复不得占用质量修订次数。建议分别记录：

```text
length_repair_count
quality_revision_count
```

字数未完成时不得生成“质量不通过”报告。字数修复次数耗尽后，保留正文草稿并进入 `LENGTH_NEEDS_ATTENTION`，明确显示实际字数、目标范围和失败原因。

## 6. 保证自动修订越改越好

### 6.1 所有版本都是候选稿

不要用新稿直接覆盖当前稿。每次生成或修订都保存为候选对象：

```python
@dataclass
class ChapterCandidate:
    content: str
    quality_score: float
    dimension_scores: dict[str, float]
    issues: list[ReviewIssue]
    length: int
    source: str  # initial / revision_1 / revision_2
```

持久化时至少保留当前最佳稿和分数轨迹；如果数据库已有候选版本表，复用并迁移，不要再增加平行的旧结构。

### 6.2 最佳稿选择规则

核心不变量：`best_quality_score` 只能保持不变或升高，绝不能降低。

```python
def choose_best(current_best, new_candidate):
    if new_candidate.quality_score > current_best.quality_score:
        return new_candidate
    if new_candidate.quality_score < current_best.quality_score:
        return current_best
    return choose_by_secondary_metrics(current_best, new_candidate)
```

同分时按以下顺序选择：

1. 字数位于目标范围内；
2. 高优先级问题更少；
3. 最低维度分数更高；
4. 改动更小、保留原有优点更多；
5. 仍相同则保留旧稿，避免无意义覆盖。

示例：

```text
初稿 91
修订稿 1 为 61 → 拒绝替换，最佳稿仍为 91
修订稿 2 为 77 → 拒绝替换，最佳稿仍为 91
最终采用 91 分稿并通过
```

### 6.3 修订必须定向进行

审核结果必须给出结构化字段：

```json
{
  "quality_score": 56.5,
  "dimensions": {
    "dialogue_voice": {
      "score": 48.0,
      "evidence": ["具体正文证据"],
      "revision_instruction": "保留情节，只调整相关对话以区分人物口吻"
    }
  },
  "issues": []
}
```

修订提示词必须包含：

- 原始章节契约；
- 当前最佳稿；
- 低分维度和正文证据；
- 必须保留的高分部分；
- 本轮允许修改的具体范围；
- 目标是超过当前最佳分，而不只是超过 60 分；
- 字数仍需保持在目标范围内。

禁止只发送一句“请根据审核意见重新规划并重写”。禁止每个小问题都触发无约束整章重写。

### 6.4 审核稳定性

审核模型应使用固定模型、固定评分模板、结构化输出和低温度（建议 `0`～`0.1`）。每项扣分必须提供正文证据。

对同一正文重复审核时，若总分波动超过预设容忍值，应记录异常并使用稳定化策略，不能把纯评分随机波动当作文章真实退化。

## 7. 旧代码清理要求

本节是强制要求。不能只让旧代码“不再调用”，必须删除或迁移，防止未来被误调用。

### 7.1 先建立旧逻辑清单

执行全仓搜索，记录每一个定义和引用：

```powershell
rg -n "READABILITY_AVERAGE_MIN_SCORE|READABILITY_DIMENSION_MIN_SCORE|QUALITY_PASS_SCORE|LENGTH_PASS_RATIO|_decision_for|decision.*REVISE|merge_review_reports|can_accept_with_warnings|preflight_only" .
rg -n "\b60(?:\.0)?\b|\b75(?:\.0)?\b|\b82(?:\.0)?\b|0\.90|0\.80" novel_agent frontend tests
```

数字搜索结果必须逐项判断含义，不能机械删除与本功能无关的数值。

### 7.2 必须删除的旧逻辑

- 删除 `READABILITY_AVERAGE_MIN_SCORE = 82` 及其所有判定分支；
- 删除 `READABILITY_DIMENSION_MIN_SCORE = 75` 作为通过门槛的所有分支；
- 删除 reviewer 各自决定最终 `PASS/REVISE` 的逻辑；
- 删除“任意 MAJOR/BLOCKER 直接质量失败”的旧分支；
- 删除将长度 `MINOR` 合并为质量失败的逻辑；
- 删除低分新稿无条件覆盖旧稿的赋值路径；
- 删除已废弃的旧提示词模板、旧工作流节点、重复 schema 和未被使用的兼容适配器；
- 删除前端根据最低项或问题严重度自行推断通过状态的逻辑；
- 删除只为旧字段服务、且当前数据已经完成迁移的 dead code。

不要保留两个同名或语义相近的质量契约。旧文件若整体废弃，应删除文件并修正所有 import、测试和文档引用。

### 7.3 防止旧代码回流

增加架构测试或静态测试，保证：

- 仓库中不再出现旧阈值符号；
- 最终状态只能由统一 `decide_quality()` 产生；
- writer、reviewer、reviser 引用同一个契约模块；
- 前端不得重新实现一遍通过规则；
- 不存在未引用的旧审核入口。

修改后再次执行 `rg`，文档中可以出现旧符号说明，但生产代码和有效测试中不得再引用。

### 7.4 数据兼容

不得直接修改或清空用户正式数据库。旧审核记录读取时可通过一个明确的只读迁移函数转换为新展示格式；新记录只能写入新格式。若无需保留旧字段，使用正式迁移脚本移除，不能在运行时代码中永久保留两套写入路径。

## 8. 前端展示修复

前端不得自行计算是否通过，只展示后端返回的最终字段：

```json
{
  "quality_score": 77.0,
  "pass_score_exclusive": 60.0,
  "quality_status": "PASSED",
  "target_length": 3000,
  "accepted_length_min": 2700,
  "accepted_length_max": 3300,
  "actual_length": 3018,
  "best_attempt_index": 1,
  "score_trajectory": [91.0, 61.0, 77.0],
  "selected_score": 91.0,
  "revision_count": 2,
  "issues": []
}
```

页面必须明确显示：

- `综合质量分 77.0 / 通过条件 > 60.0`；
- `质量审核已通过`，不能再显示“未通过审核”；
- 实际字数与目标范围；
- 每轮候选分数和最终选中版本；
- 扣分问题及证据；
- 当前处于字数补写、质量修订还是等待用户处理。

不得只显示“最低项 76.5”而隐藏统一总分。不得把 `91 → 61 → 77` 的最后一个数字误认为最终采用版本；应显示“最终采用：91 分（第 1 版）”。

修复截图中审核区域宽度过窄导致中文逐字竖排、按钮挤压和信息不可读的问题。卡片宽度由布局决定，不允许用户拖动造成错位；长文本正常换行，操作区保持可点击。

## 9. 推荐实施顺序

1. 全仓搜索并绘制当前实际调用链，确认生产入口、后台任务入口和前端数据来源。
2. 为现有错误行为补充失败测试，确保能够复现 77 分未通过、87% 字数误归类、91 分稿被覆盖等问题。
3. 建立唯一 `ChapterQualityContract` 和唯一 `decide_quality()`。
4. 重构统一评分结果 schema，先改后端判定，再改前端展示。
5. 让初稿生成、审核和修订读取同一契约。
6. 实现字数统计、定向补写及复检闭环。
7. 实现候选稿和单调最佳稿选择。
8. 删除旧阈值、旧判定函数、旧提示词和旧状态分支。
9. 完成数据库/序列化兼容处理，但不触碰用户正式数据。
10. 更新前端审核面板。
11. 执行单元、集成、接口和前端测试。
12. 更新 `docs/USER_GUIDE.md`，并验证 README 中的用户指南链接仍然有效。
13. 再执行一次全仓搜索，确认生产代码不存在旧符号和旧入口。

## 10. 必须补充的测试

### 10.1 质量判定单元测试

- `60.0` → 不通过；
- `60.01` → 通过；
- `77.0` 且有 `MINOR` → 通过；
- `77.0` 且某单项低于 75 → 仍按总分通过；
- `77.0` 且可读性平均低于 82 → 仍按总分通过；
- 不允许任何 reviewer 的局部 decision 覆盖统一结论。

### 10.2 字数测试

- 目标 3000，正文 2700～3300 → 达标；
- 正文约 2610 → 进入定向补写，不进入质量失败；
- 正文低于 2100 → 进入严重不足恢复；
- 补写后重新计数并进入审核；
- 字数补写不消耗质量修订次数；
- 前后端对同一正文计算出的字数一致。

### 10.3 单调修订测试

- `91 → 61 → 77` 最终选择 91；
- `56 → 68` 最终选择 68 并通过；
- `56 → 54 → 59` 最终选择 59，并在次数耗尽后进入 `QUALITY_NEEDS_ATTENTION`；
- 同分时选择字数合格、问题更少的版本；
- 低分新稿不会覆盖数据库中的高分最佳稿。

### 10.4 第一章测试
